# ADR-002：中央 Workbench 壳层与可选任务环境

状态：已接受
日期：2026-08-21

补充说明：本 ADR 继续描述当前已实现壳层。2026-08-24 获批的 v2 目标信息架构由 `ADR-004-new-task-first-release-gate.md` 管理；Batch 5A 已把分离的“概览 / 运行状态”合并为“运行”，Batch 9 已把原“快速助手”原位演进为“任务环境”，Batch 10 已通过专用 Vault 技术运行门。

## 决策背景

早期插件骨架把 Workbench 直接放入 Obsidian 右侧叶片，适合验证原生 `ItemView`，但不能承载用户设想的多工作台结构。已确认的长期形态是在 Obsidian ribbon 中提供入口，在中央标签页内建立插件自有左导航，并逐步容纳任务、阅读、资讯和领域工作台。右侧边栏只作为可选的快速助手。

当前架构只承载已经实现的“新建任务 / 运行”与按需任务环境；未来模块、Vault 写入、任意 Shell、移动端和发布仍受独立批准门约束。

## 决策

1. ribbon 和“打开工作台”命令调用 `workspace.getLeaf('tab')`，打开或复用唯一的中央 Workbench 标签页。
2. Workbench 在自己的 ItemView 内渲染 `194px` 本地左导航和主内容区；当前只启用“新建任务”“运行”。
3. 未实现模块不进入插件导航；继续不建立公共模块注册器、动态加载器或数据协议。
4. DSH 健康检查与当前连接真值统一归入“运行”，同时保持“可执行”不等于“已连接”的边界。
5. 原快速助手沿用既有 view type 与命令 ID，原位演进为独立“任务环境” ItemView；只能由显式命令在右侧打开或复用，投影公开健康/连接、已选笔记、工作区名称、权限、工具和最近变更，不提供第二套主对话或唯一确认。
6. UI 规则由根目录 `DESIGN.md` 管理，逐批证据由根目录 `design-qa.md` 管理。

## 原因

- 中央标签页为未来多个工作台提供足够的主内容空间，同时遵循 Obsidian 的宿主结构。
- 本地导航让模块层级保持稳定，不把产品导航挤进 Obsidian 全局侧边栏。
- 可选任务环境适合轻量状态和上下文提示，但不会把主产品退化为聊天侧栏。
- 静态的最小导航模型已经满足两个真实页面；当前没有两个以上动态模块消费者，不应提前建立公共扩展框架。
- 禁用规划入口和空状态可以表达方向，又不制造虚假功能。

## 被否决方案

### Workbench 常驻右侧边栏

否决。主内容空间过窄，无法稳定承载未来仪表盘、阅读和资讯面板，也与已确认的信息架构冲突。

### 复制独立桌面应用的全套外壳

否决。插件不应重建 Obsidian 的标题栏、ribbon、标签栏和全局设置。

### 立即建立通用模块市场或动态注册器

否决。当前只有两个真实页面，没有足够消费者证明公共抽象必要；未来模块仍需逐批批准。

## 后果与边界

- 用户从 ribbon 打开的是中央 Workbench；任务环境只通过单独命令按需打开。
- 当前导航、正式会话和任务环境只授权已实现的只读知识库、真实对话及单一 Vault 外工作区任务；不授权连接器、自动化、资料库、领域工作台、Vault 写入或任意 Shell。
- 后续若引入实际模块，需要重新评估导航契约、持久化、权限、安全、移动端和 CI，不得仅把禁用状态改为可用。

## 验证

- 单元测试证明中央标签页创建、重复打开复用、“新建任务 / 运行”导航切换、未实现入口不渲染，以及右侧任务环境按需创建和复用。
- `npm test` 在 Windows 与 Ubuntu GitHub Actions 中执行这些测试。
- 专用隔离 Vault 验收证明 ribbon/命令、正式会话、任务环境、宽窄布局、深浅主题、错误恢复与同步卸载零残留。
