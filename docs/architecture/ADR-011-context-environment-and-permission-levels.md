# ADR-011：上下文、工作环境与权限级别分层

- 状态：已接受的后续产品决策，尚未实现
- 日期：2026-08-31
- 关联：[ADR-005](./ADR-005-new-task-v1-host-contract.md)、[ADR-010](./ADR-010-formal-conversation-and-task-environment.md)
- UI 审阅真相：Ardot 文件 `718186366720195`、页面 `UI 真相 v2`（`12:1`）；Ardot 未修改、只读核对

## 用户结果

用户不再需要把“知识库”“工作区”和“权限”理解为同一组互斥模式。输入区分别表达本次参考资料、可工作的资源范围和运行权限级别，使“知识笔记”等后续使用场景能够在当前 Obsidian Vault 中自然读写，同时让超出已选环境的访问边界保持可解释。

## 背景

当前 v1 将“对话/任务执行”模式、只读 Vault 上下文、Vault 外可写工作区和逐请求授权绑定在一起。这是 Batch 6–10 已实现并验证的历史契约，但把三种不同概念压在同一个选择层级中：

1. 本次请求要引用什么资料；
2. 智能体可以在哪些资源中工作；
3. 智能体以何种权限级别运行。

后续产品需要支持把对话、附件和外部内容结构化整理为知识笔记。如果继续把“仅知识库”“仅工作区”“知识库只读”和“完全权限”作为同级权限选项，用户会被迫用权限菜单重复表达工作环境，也难以理解选择一篇笔记与允许修改当前知识库之间的区别。

## 决策

### 1. 三层概念

后续产品模型固定分为三层：

| 层级 | 回答的问题 | 产品对象 |
| --- | --- | --- |
| 上下文 | 本次运行参考什么 | 附件、选中的笔记、选中的文件夹及其确定内容快照 |
| 工作环境 | 本次运行可以在哪里工作 | 当前 Obsidian Vault 与用户显式选择的外部工作区 |
| 权限级别 | 超出工作环境时如何处理 | 标准权限、完全权限 |

这三层不得重新合并为一个“模式”枚举。“知识笔记”“日常任务”等使用场景只负责提供任务入口、快捷功能和合理默认值，不另建一套运行权限。

### 2. 当前知识库

- 插件所在的当前 Obsidian Vault 自动成为“当前知识库”，用户不需要在每次发送前重复添加。
- 当前知识库在后续标准权限下具备读写能力；这表示能力范围，不表示每个请求都会修改笔记。
- 内置知识库写入应由插件通过 Obsidian API 执行，以便保持当前编辑状态、元数据、链接、同步和文件事件的一致性。
- 用户选择笔记或文件夹只是在本次请求中缩小或补充上下文，不新增权限，也不要求修改这些来源。
- 附件默认是只读输入；除非用户后续明确选择导入或生成 Vault 产物，不修改附件源文件。
- 其他未打开的 Vault 不冒充当前 `app.vault`。未来若支持外部 Vault，必须另行决定切换 Vault、外部文件访问或专用桥接机制。

### 3. 外部工作区

- 外部工作区是用户显式选择的 Vault 外目录，属于工作环境而不是权限级别。
- 是否选择外部工作区不改变当前知识库的存在；没有外部工作区时，知识库场景仍可在当前 Vault 中完成。
- 外部工作区的选择、身份校验、运行数据边界和文件变更账本继续采用显式且可核对的路径身份，不把完整绝对路径写入普通 UI 或 Vault。

### 4. 权限级别

后续权限选择器只保留两个用户级选项：

- **标准权限**：当前知识库可读写；已选择的外部工作区可读写；访问这些环境以外的资源时由运行时发起越界授权。
- **完全权限**：移除文件系统工作环境边界，允许访问当前 Windows 用户能够访问的全部磁盘位置；仍受操作系统 ACL、UAC、文件占用和账户身份限制。

“仅知识库”“仅工作区”和“知识库只读”不再作为与标准/完全同级的权限档位。如果以后需要只读知识库，它应作为知识库自身的访问属性或独立安全开关，而不是第三个运行权限层级。

### 5. 尚未决定的权限维度

本 ADR 只确认概念分层、当前 Vault 的知识库身份以及完全权限的全磁盘语义。以下内容仍待用户讨论和明确批准：

- 标准权限与完全权限是否开放 Shell，以及 Shell 的命令、工作目录、子进程和环境变量边界；
- 两个权限级别是否开放网络，以及是否采用关闭、按需授权、域名白名单或完全开放；
- 完全权限下 DSH 的原始文件工具能否直接修改 Vault，还是仍要求知识库操作通过 Obsidian API；
- Vault 新建、追加、覆盖、移动、删除和批量变更分别采用预授权、运行中确认、事后审核或撤销中的哪一种机制；
- 权限选择只作用于当前会话，还是可保存为后续新会话的默认值。

在这些问题确认前，产品文档和 UI 不得把 Shell、网络、无确认 Vault 写入或 DSH `danger-full-access` 宣称为已批准能力。

## 与当前实现的关系

- 本 ADR 是后续产品方向，不改变 Batch 6–10 已实现的“只读 Vault 上下文 + 单一 Vault 外可写工作区 + 逐请求授权”能力真相。
- 当前源码、bridge 协议、测试、隔离 Vault 证据和 DSH `0.1.1-rc.2` 兼容声明均未因本 ADR 自动改变。
- ADR-005 与 ADR-010 继续作为现有 v1 的历史及实现契约；后续实施批次必须显式列出被替代的条款，并同步代码、协议、持久化、测试、CI、`DESIGN.md`、需求基线和安全披露。
- 本次没有修改 Ardot。只有用户明确授权后，才允许把该分层同步到 Ardot UI 真相。

## 验收与停止边界

本决策批次只要求：

1. 本 ADR 完整记录已确认概念与未决问题；
2. `DESIGN.md` 链接本 ADR，并明确“尚未实现、Ardot 未修改”；
3. 不修改源码、bridge、测试、Vault、运行时配置或 Ardot；
4. 不把文档决策冒充为插件已具备知识库写入、标准权限或完全权限。
