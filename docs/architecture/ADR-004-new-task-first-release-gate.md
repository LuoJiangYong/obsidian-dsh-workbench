# ADR-004：新建任务主入口、运行合并与首个社区发布门

状态：已接受
日期：2026-08-24

## 决策背景

现有运行实现以“概览”和“运行状态”验证了中央 Workbench 壳层、只读 DSH 健康检查和可选快速助手，但它还不是插件的首发核心工作流。用户已经明确：主产品应参考任务型工作台结构，以“新建任务”承载 DeepSeek Harness 对话、任务执行和上下文；“概览”和“运行状态”不应继续占用两个一级入口。

本 ADR 只固定产品信息架构、发布门和后续实现边界，不授权在当前设计批次实现 DSH 会话、任务执行、Vault 访问或社区发布。

## 决策

1. “新建任务”固定为 Workbench 内部导航第一个功能，是唯一主对话与任务入口。
2. “新建任务”的首发职责包括：DeepSeek Harness 对话、任务目标、执行过程、上下文选择、权限审阅、拟变更审阅、取消和明确错误状态。
3. “项目”“专家 · Skill · 连接器”“自动化”“资料库”“领域工作台”保持未开放；需要保留导航结构时，只使用浅灰文字与图标和真实禁用语义，不能显示“规划中”等开发进度，也不能为了填充导航加载假数据或建立无消费者的公共模块框架。
4. 原“概览”和“运行状态”合并为“运行”，固定在功能导航最后；它同时展示当前能力真值和受限的 DSH `--version` 健康检查。
5. 右侧快速助手保持可选，只用于健康、当前上下文和快捷提问，不承担主对话；产品标题不附加发布阶段说明。
6. 左上角品牌名称固定为三行：第一行 `DeepSeek`、第二行 `Harness`、第三行 `Workbench`；插件身份继续使用 DeepSeek 鲸鱼图标。
7. Ardot 产品画板和 Obsidian 插件界面不显示“首发”“规划中”“尚未实现”等开发阶段、发布批次或治理审批文案；发布门和实现差异只记录在治理文档、测试、CI 与验收证据中。
8. 首个 Obsidian 社区插件发布功能固定为“新建任务”。进入社区发布审批前必须完成：
   - 功能和错误状态完整实现；
   - 单元、契约、协议、安全、Windows 进程和隔离 Vault 验收按行为需要补齐；
   - 双平台 CI 实际执行相应测试并成功；
   - 用户对最终 Obsidian 运行 UI 明确验收通过。

## 原因

- 把用户最常用的“开始一次 Harness 工作”放在第一入口，减少从状态页绕行。
- 把只读概览和健康检查合并，降低一级导航重复并保持能力真相集中。
- 主对话与快速助手分工明确，避免右侧边栏取代中央工作台。
- 发布门绑定可运行的首发核心和用户 UI 验收，避免用设计稿、CI 或 Release 代替产品完成度。

## 后果与边界

- Ardot `UI 真相 v2` 和 `DESIGN.md` 已体现本决策。
- 当前源码与单元测试已同步新导航、新建任务宿主页面、确定性状态骨架和快速助手；Batch 5A 隔离 Vault 宿主 UI 运行证据已通过。
- DSH 输入、事件、状态、取消、错误、权限和日志脱敏契约已由 ADR-005、bridge 协议 v1 与 Batch 3–4 实现固定；后续批次继续接通真实产品行为。
- 未经新批准不得读取或写入 Vault，不得建立任意 Shell，不得安装或更新 DSH，不得创建 Release 或提交 Obsidian 社区目录。
- “运行”当前是审阅名称；若后续改名，必须同步 Ardot、`DESIGN.md`、ADR、实现、测试、CI 契约和 `design-qa.md`。

## 验证

- `tests/contracts.test.ts` 固定“新建任务首位”“运行最后”“三行品牌”、宿主 UI 已同步但模型未接通的能力边界和首发门。
- `scripts/verify-ci-coverage.mjs` 确认双平台完整 `npm test` 实际执行治理契约。
- `design-qa.md` 记录 Ardot v2 六个产品画板、同屏参考对照、来源资产和布局诊断结论。
