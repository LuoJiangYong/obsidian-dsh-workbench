# 开发宪法评估

更新时间：2026-08-21

## 结论

项目采用根目录 `AGENTS.md` 作为所有开发会话的最高项目级宪法。它继承 Hermes Skill 开发方法论中的事实来源、第一性原理、精准修改、审批门控微批次、依赖同步和验证闭环，但针对 Obsidian 社区插件、外部 DeepSeek Harness 运行时、Vault 数据安全与 Windows 子进程进行了实质调整。

本评估描述治理决策，不代表插件功能已经实现。

## 从 Hermes 方法论继承的原则

| 原则 | 在本项目中的落地 |
| --- | --- |
| 一个模块一个职责 | UI、运行时适配、Vault Bridge、进程管理和发布验证分别保持明确边界 |
| 共享稳定契约 | UI 只消费 `RuntimeAdapter` 和标准事件，不解析供应商私有 stdout |
| 真实痛点出现后再抽象 | SDK、ACP 与 bridge 不并行建设三套生产实现；P0 后只保留一条主路线 |
| 第一性原理六问 | 重要功能和架构变化必须定义用户结果、约束、最小机制、证据和成功证明 |
| AI 编码四原则 | 先想再写、极简优先、精准修改、目标驱动 |
| 对抗式审查 | 每批重点审查越权读取、未确认写入、残留进程、凭据泄露和协议漂移 |
| 审批门控微批次 | 每批只有一个可验证结果，完成验证、提交和 CI 后停止 |
| 依赖同步 | 公共协议、配置、文档、测试和 CI 必须在同一批次检查 |

## AI 代码开发原则的完整落地

用户于 2026-08-21 单独批准把 AI 代码开发原则写入项目宪法。根目录 `AGENTS.md` 以可执行规则而非口号规定四项原则：

### 先想再写

编码前必须定义用户结果、允许与禁止范围、输入输出、状态、失败行为、事实与假设以及验证命令。不能把未确认假设、占位实现或假数据静默固化进代码。

### 极简优先

只实现当前验收需要的最小机制；不为未来需求增加抽象、配置和 fallback；没有两个真实消费者与重复痛点时不抽公共层；失败必须可见，不能通过错误吞噬制造表面稳定。

### 精准修改

每处 diff 必须映射到当前验收条件；不顺便重构或格式化；保留用户工作；公共契约变化同步检查类型、注册、配置、持久化、下游、文档、测试与 CI。

### 目标驱动

从失败或契约基线出发，完成最小改动、相关测试、完整质量门、依赖检查、清理、diff 复核、精确提交和远端 CI 后才算闭环；到达批准边界必须停止。

### 明确禁止的 AI 行为

- 编造 API、事件、平台能力或测试结果。
- 用 `any`、无界断言、空 catch、宽松 fallback 或降低断言强度掩盖问题。
- 用 mock 结果冒充真实 DSH、Windows、Obsidian 或发布验收。
- 未经批准安装依赖、修改真实 Vault、提交、发布或扩大副作用。
- 创建无当前消费者的通用框架，或留下未披露的 TODO 和临时路径。

### 与 CI 的强制关系

每次代码变化都必须建立“行为变化 → 测试 → workflow 实际执行”的证据链。缺少任一环时，必须在同一批次补齐，否则不能标记完成。平台、协议、安全、Vault 和 Release 边界变化还必须触发对应 CI 矩阵复查。

## 针对 Obsidian 与 DSH 的调整

### Vault 不是普通工程目录

Hermes Skill 方法论通常面向代码或 Skill 文件；本项目面对个人知识资产，因此新增以下硬边界：

- Vault 默认只读。
- 写入必须经过 proposal、路径和版本校验、diff、用户确认、Obsidian API 写入和读回。
- DSH 不得默认以整个 Vault 为可写 `cwd`。
- 会话、缓存、索引、日志和凭据必须位于 Vault 外。
- 破坏性测试只能使用隔离 Vault。

### 外部运行时需要明确生命周期

插件不是 DSH 安装器。项目新增：

- 禁止自动安装或更新 DSH、Node、Python 和其他运行时依赖。
- 锁定 DSH 版本并维护协议兼容矩阵。
- Windows `.cmd` shim、隐藏窗口、启动超时、取消、关闭和无残留进程均为发布阻断条件。
- SDK、ACP、Cordis bridge 的能力只能依据当前官方契约和 P0 实测。

### 社区审核是产品边界的一部分

Obsidian 当前政策禁止客户端遥测和插件自行安装或更新依赖，并要求在 README 披露网络、账号及 Vault 外文件访问。宪法因此把隐私披露、外部依赖、桌面端限制、非官方身份和 Release 一致性设为硬门，而不是发布前临时补文档。

官方依据：

- [Obsidian Developer policies](https://docs.obsidian.md/community-directory/developer-policies)
- [Submission requirements for plugins](https://docs.obsidian.md/community-directory/submission-requirements-for-plugins)
- [Submit your plugin](https://docs.obsidian.md/plugins/releasing/submit-plugin)

### CI 必须伴随实现共同演进

Hermes 方法论把 CI 视为宪法执行器；本项目进一步规定：

- 每个行为变化都要判断现有 CI 是否真正执行对应测试。
- 缺少测试或 workflow 覆盖时，必须在同一批次补齐。
- 平台、协议、安全和发布边界变化时，必须复查完整 CI 矩阵。
- 本地与 CI 共用验证脚本。
- 远端成功与 `0 annotations` 是批次完成证据，但不自动批准下一批。

## 暂不适用或暂缓的原则

| 方法论内容 | 当前处理 |
| --- | --- |
| L3 Skill 的 `SKILL.md` 路由中枢 | 本项目是 Obsidian 插件，不创建项目级 Skill 路由文件 |
| 案例库与多维索引 | 当前没有案例检索需求，延期 |
| 多文件 YAML 元数据体系 | 初始工程规模小，使用文件结构、Git、ADR 和自动验证即可 |
| 动态 inventory 工具 | 没有发生人工清单漂移，暂不引入 |
| 每个 Phase 独立会话 | 作为建议而非硬规则；真正硬门是每个批准微批次的停止边界 |

## 如何执行而不是停留在文字

| 宪法规则 | 自动或人工执行方式 |
| --- | --- |
| 固定 name、id、桌面端 | manifest 契约测试与版本一致性脚本 |
| 能力真相 | 治理契约测试检查 ADR、README 和发布状态用语 |
| Vault 默认只读 | Vault Bridge 权限和路径测试；未实现前保持功能缺失而非开放式替代 |
| proposal 后写入 | proposal 状态机、base hash 和 diff 测试；隔离 Vault 人工验收 |
| 进程无残留 | 假运行时集成测试、Windows 进程树测试和插件禁用验收 |
| 无遥测和敏感信息 | 依赖审查、边界脚本、凭据扫描和日志脱敏测试 |
| 发布声明真实 | manifest、README、versions、tag 和 Release 资产一致性检查 |
| CI 伴随演进 | 每批 DoD 强制检查测试到 workflow 的执行链，并更新 `docs/ci-cd-roadmap.md` |
| AI 代码开发原则 | 契约测试检查原则存在；评审逐项核对事实、范围、diff、测试和 CI 证据 |
